# Roadmap

The roadmap is ordered by compatibility risk. A milestone is complete only when
its behavior is covered by deterministic tests and still preserves the
architecture invariant:

```text
GoldSrc packets -> ClientWorldState -> RenderScene -> Renderer
```

The Windows x86 Visual Studio 2022 acceptance build remains required throughout
the roadmap. Later platform support may be additive.

## M0 — Project/bootstrap

**Goal:** establish a debuggable Win32 foundation without pretending that a
network protocol client already exists.

Deliverables:

- Visual Studio 2022 multi-config solution generated by CMake;
- Win32 Debug, Release, and RelWithDebInfo configurations;
- grouped application, engine, test, and third-party `.vcxproj` targets;
- C++20 with MSVC `/W4` and `/permissive-` on project targets;
- optional project-scoped `HLCLIENT_WARNINGS_AS_ERRORS`;
- SDL3 window/event/context layer and automatic runtime DLL deployment;
- OpenGL 3.3 Core bootstrap through a pinned generated GLAD2 loader;
- basic logging, command-line parsing, game-path validation, byte I/O,
  IPv4 address/UDP foundations, neutral world state, and render scene;
- pinned Half-Life SDK reference submodule on an isolated `SYSTEM` header
  boundary;
- Catch2/CTest tests that need neither a public server nor installed game data;
- documented manual and preset build/F5 workflows plus Windows CI.

Explicitly not included: `getchallenge`, live `connect`, sign-on, resource
download, packet sequencing, entity parsing, asset loading, gameplay, or SDK
game DLL execution. The M0 `--connect` option validates intent only.

Exit criteria:

- `build/hl-client-engine.sln` is generated with Visual Studio 17 2022 / Win32;
- Win32 Debug builds cleanly and `hlclient` is the startup project;
- F5 launches with the repository root as working directory and finds SDL3;
- CTest passes in Win32 Debug;
- command-line help/version paths run without an installed Half-Life copy.

## M1 — Connectionless protocol

**Goal:** interoperate with the connectionless discovery/challenge surface of an
original HLDS without entering the stateful sign-on channel.

Planned work:

- encode and decode the `0xFFFFFFFF` connectionless packet envelope;
- bounded parsing for challenge and informational responses needed by the
  client path;
- UDP send/receive polling, timeouts, retries, cancellation, and endpoint
  validation;
- explicit connection state and diagnostic logging;
- capture-derived or synthetic fixtures with no dependency on a live server;
- optional manual interoperability test against a user-run original HLDS.

Exit criteria: a malformed datagram cannot overrun or allocate without bounds,
and a valid original HLDS challenge exchange is reproducible and observable.

## M2 — Challenge, connect, and sign-on

**Goal:** enter and maintain the sequenced GoldSrc client channel through the
initial sign-on stages.

Planned work:

- construct the client connect request from challenge/session parameters;
- implement sequence numbers, acknowledgements, reliable state, fragmentation,
  timeout, and disconnect handling required by the target protocol;
- parse serverdata and sign-on messages into project-owned session state;
- expose transitions to `ClientWorldState` without leaking packet structs;
- redact sensitive connection values from logs where appropriate;
- state-machine tests for loss, duplicate, reordering, truncation, and timeout.

Exit criteria: the client reaches the defined pre-resource sign-on state against
an original compatible HLDS and fails closed on malformed streams.

## M3 — Resource and precache pipeline

**Goal:** negotiate, validate, and prepare the server-required resource set.

Planned work:

- parse resource lists and consistency metadata;
- map approved resources into sandboxed game/search paths;
- implement bounded fragments/downloads where protocol compatibility requires
  them, with traversal and overwrite protection;
- verify sizes and available checksums before accepting content;
- represent precache entries with engine-owned handles;
- cache behavior and synthetic resource-list tests.

Exit criteria: required resources resolve deterministically from a user-owned
installation or a safe download cache, and remote names cannot escape approved
roots.

## M4 — BSP and WAD world rendering

**Goal:** load and render a GoldSrc world using user-supplied assets.

Planned work:

- bounded BSP parsing for the required Half-Life format/lumps;
- WAD texture lookup and decoding;
- visibility, world surfaces, texture/lightmap upload, and static geometry;
- coordinate-system and gamma/lightmap conventions captured in tests;
- missing/corrupt asset diagnostics with no renderer-side file parsing;
- CPU asset structures translated into renderer resources.

Exit criteria: a representative user-owned Half-Life map renders repeatably,
and parser tests cover corrupt offsets, counts, dimensions, and lump lengths.

## M5 — Entity snapshots

**Goal:** decode live server entity state and present it as stable interpolatable
world data.

Planned work:

- delta descriptions/baselines and packet-entity messages;
- snapshot history keyed by server time and sequence;
- lifecycle for create, update, dormant, and remove operations;
- player and non-player entity separation where the protocol requires it;
- loss/reordering recovery and bounded entity indices/counts;
- translation from protocol fields to neutral entity components.

Exit criteria: recorded snapshot fixtures reproduce the expected neutral world
state without any packet type reaching the renderer.

## M6 — MDL, players, and animated models

**Goal:** render server entities with GoldSrc studio models and basic animation.

Planned work:

- safe MDL and related texture/sequence parsing;
- bones, sequences, controllers, blending, bodygroups, and skins needed by
  Half-Life multiplayer;
- player model selection and entity attachment basics;
- render-scene instances and renderer-side GPU resource caching;
- invalid model/animation fallback behavior.

Exit criteria: representative player and world studio models animate from
snapshot state with parser and pose tests independent of OpenGL.

## M7 — Input, user commands, and movement

**Goal:** turn SDL input into GoldSrc-compatible client commands and local
movement state.

Planned work:

- device-independent input actions, bindings, focus, and mouse capture;
- fixed protocol representation for `usercmd` construction and transmission;
- command numbering, view angles, buttons, impulse, and movement values;
- client-side movement using reviewed compatibility rules;
- repeatable command-generation tests and input sampling policy;
- clear boundary between platform events, command intent, and wire encoding.

Exit criteria: the client can join, spawn, and send valid commands while local
movement state remains deterministic under the test clock.

## M8 — Interpolation and prediction

**Goal:** provide smooth presentation under real network timing while remaining
correctable by authoritative server state.

Planned work:

- snapshot interpolation buffer and render-time selection;
- local-player prediction, command history, acknowledgement, and replay;
- authoritative correction with bounded smoothing/error metrics;
- entity-specific interpolation/teleport rules;
- loss, latency, jitter, and frame-rate simulation tests;
- instrumentation to distinguish network, simulation, and render time.

Exit criteria: movement stays responsive and converges to authoritative state in
repeatable simulated adverse-network scenarios.

## M9 — `client.dll` API and HUD

**Goal:** support the client-facing game API and essential Half-Life HUD/game
presentation behavior through an explicit compatibility layer.

Planned work:

- define an x86 ABI boundary for the required `client.dll` exports/callbacks;
- isolate unsafe module loading and function pointers behind checked adapters;
- implement the minimal engine function table needed by the target game;
- user messages, HUD state, text, sprites, console, and basic menus;
- prevent SDK ABI types from leaking into renderer and networking contracts;
- test with project-owned mock modules before user-supplied game binaries.

Exit criteria: a licensed user-supplied compatible `client.dll` initializes and
drives the required HUD path without becoming the engine's internal API.

## M10 — Sound and effects

**Goal:** reproduce the audio and transient visual feedback needed for a coherent
multiplayer session.

Planned work:

- sound precache/playback, channels, attenuation, looping, and listener state;
- WAV decoding/validation and SDL audio integration;
- sprites, beams, dynamic lights, decals, particles, and temporary entities;
- event/message translation into neutral audio/effect commands;
- resource caps and graceful fallback for missing or malformed assets.

Exit criteria: representative multiplayer events produce synchronized sound and
effects while headless parser/simulation tests remain available.

## M11 — Playable original Half-Life multiplayer

**Goal:** deliver an end-to-end standalone session against an original HLDS.

Planned work:

- close remaining sign-on, gameplay message, scoreboard, chat, spectator, and
  disconnect/reconnect gaps;
- configuration, console commands/cvars, bindings, and usable diagnostics;
- stability under map changes, death/respawn, packet loss, long sessions, and
  normal server population;
- compatibility matrix for explicitly tested original server/game versions;
- performance, memory, parser fuzzing, and packaging/license review.

Exit criteria: a user can launch the Win32 client, connect to an original
Half-Life multiplayer server with licensed local assets, join play, interact,
change maps, and disconnect cleanly.

## M12 — `hl.exe` injection bridge prototype

**Goal:** prove that the architecture can consume a 32-bit in-process Half-Life
state provider without forking the client/render core.

Planned work:

- separate Win32 x86 bridge/injector prototype with explicit process and module
  compatibility checks;
- narrow, versioned bridge messages translated into project-owned state;
- lifecycle, thread, exception, and teardown containment;
- no injected pointers, private layouts, or SDK structs in renderer APIs;
- standalone and bridge providers selectable without changing render backends;
- security, anti-cheat, Steam terms, redistribution, and legal review before any
  public distribution or broader testing.

Exit criteria: on an explicitly supported user-owned 32-bit `hl.exe` build, the
prototype can start and stop safely and feed the same world/scene pipeline used
by standalone networking. This milestone is a research prototype, not an
authorization to bypass platform protections or deploy into third-party
processes without consent.

## Cross-cutting gates

Every milestone retains these gates:

- Visual Studio 2022 / MSVC v143 / Win32 Debug builds and CTest pass;
- no dependency on `Pvitaly91/hl-engine` or server implementation code;
- malformed remote/file input is treated as untrusted and tested at boundaries;
- third-party and game-content licenses remain separate and documented;
- renderer APIs remain independent of GoldSrc packets and injection details;
- live-server and installed-game checks are optional manual interoperability
  tests, never prerequisites for the deterministic automated suite.
